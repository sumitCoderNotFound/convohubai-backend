# Database Migrations (Alembic)

Alembic is already configured: `alembic.ini` plus `alembic/env.py`, which imports
`app.models` so every table (core + recruitment + ATS) is visible to autogenerate.

In development the app also calls `create_all` on startup, which creates missing
tables but never alters existing ones. For production, use Alembic instead.

## One-time: create the baseline migration
Run against your real Postgres (uses DATABASE_URL_SYNC):

    cd backend
    alembic revision --autogenerate -m "baseline schema"
    alembic upgrade head

This generates a versioned migration in `alembic/versions/` that matches the
current models, and applies it.

## After any model change
    alembic revision --autogenerate -m "describe the change"
    # review the generated file in alembic/versions/, then:
    alembic upgrade head

## Useful commands
    alembic current          # show applied revision
    alembic history          # list migrations
    alembic downgrade -1     # roll back one step

## Notes
- Always review autogenerated migrations before applying; Alembic can miss some
  changes (server defaults, certain type changes, indexes).
- Phase 11 added no new columns (it reuses existing fields), so no migration is
  required for it. Earlier phases that added tables (e.g. ats_connections,
  ats_mappings) are picked up by the baseline autogenerate above.
- For production, disable the startup create_all once migrations are the source of
  truth, so schema changes only happen through reviewed migrations.

## Phase 14 - interviewer avatar (one new column)
Phase 14 adds `interviewer_avatar_url` to `recruitment_settings`. New databases get it
via create_all. For an EXISTING database, add it once:

    ALTER TABLE recruitment_settings ADD COLUMN IF NOT EXISTS interviewer_avatar_url VARCHAR(500);

(or run `alembic revision --autogenerate -m "interviewer avatar" && alembic upgrade head`.)
